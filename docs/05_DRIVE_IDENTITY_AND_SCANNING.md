# 05. Drive Identity and Scanning

## Drive identity model

A drive has two identities:

1. **Internal UUID**, generated by the app and never reused.
2. **Physical drive number**, assigned by the user and printed on the drive.

The drive number is the primary human reference. The UUID prevents collisions and supports renumbering.

## Drive manifest

With permission, create:

```text
.atlasdrive/drive.json
```

Minimum fields:

```json
{
  "schemaVersion": 1,
  "driveId": "uuid",
  "driveNumber": 14,
  "friendlyName": "AtlasDrive A",
  "createdAt": "2026-07-23T23:00:00Z",
  "lastSuccessfulScanAt": null,
  "appId": "atlasdrive"
}
```

The manifest must be written atomically through a temporary file inside the app-owned folder and then renamed. Do not write elsewhere on the drive.

## Recognition signals

Use several signals rather than trusting a single file:

- drive manifest UUID
- macOS volume UUID
- filesystem type
- capacity
- current volume name
- selected structural fingerprints
- sample of known relative paths and sizes

## Conflict states

### Manifest copied to another drive

If the same internal UUID appears on two simultaneously connected physical volumes, mark both as an identity conflict. Do not silently choose one.

### Backup clone

Allow the user to declare a drive as a backup clone. Give it a distinct internal UUID and physical drive number while recording the relationship.

### Manifest missing

Use secondary signals to suggest a likely match, then ask the user to restore the manifest. Never assign identity solely from a volume name.

### Drive renumbered

Update the local record and manifest, preserving historical references in an audit table.

## Scan modes

### Initial scan

- enumerate supported files
- record pre-processing stat values
- populate durable queue
- process batches
- verify originals and outputs

### Incremental scan

- compare directory state and known files
- queue new files
- queue changed files for re-analysis
- mark missing files without deleting their historical record
- avoid reprocessing unchanged files

### Validation scan

- verify a sample or all source files still match stored stat and optional content hash
- verify local thumbnails and catalogue consistency

## Supported image types

Start with formats reliably decoded by the chosen local stack. At minimum target:

- JPEG
- PNG
- HEIC or HEIF
- TIFF
- WebP

RAW support should be staged. Initially use embedded previews where safe and clearly label this limitation.

## Traversal safety

- Resolve and validate canonical paths.
- Stay beneath approved scan roots.
- Do not follow symlinks outside approved roots.
- Detect recursive mount points and package boundaries.
- Skip the app-owned `.atlasdrive` folder.
- Provide configurable exclusions.
- Treat inaccessible files as structured failures, not fatal crashes.

## Source integrity snapshot

Before processing a file, capture:

- size
- modification time with highest available precision
- creation time where available
- optional inode or file identifier

After processing, recapture and compare. Any change caused during indexing is a hard failure. External user changes should be distinguished where possible, but safety takes priority.
